# Milestone C3.3 — Gate 5 Visibility Transition Detection

## Date: Current session
## Status: COMPLETE (reviewer PASS, infra_verifier PASS, all tests pass)

## Problem
Gate 5 used MutationObserver only to detect observable application behavior during hover.
For CSS-only `:hover` mega-menus (e.g. Adani One: pure `:hover` pseudo-class on `<li>` toggling
`display: none` → `display: block` on sibling `<ul>`), zero DOM mutations occur.
Both 'Services' and 'Flights' hovers were rejected by Gate 5 → missing from recordings.

## Solution
Added **Visibility Transition Detection** as Mechanism 2 for Gate 5, alongside existing
MutationObserver (Mechanism 1). OR logic: either qualifying → Gate 5 passes.

### How it works
1. At mouseenter: take `getComputedStyle()` snapshot of `target.parentElement` subtree
   (captures display, visibility, opacity for every element)
2. At dwell timer fire (500ms): take a second snapshot, compare element-by-element
3. If any element transitioned from invisible (display:none | visibility:hidden | opacity:0)
   to visible → qualifies as observable behavior

### Why parentElement scope
CSS `:hover` mega-menu patterns place the submenu as a SIBLING of the hover target
inside a common parent `<li>`. The hover target itself (e.g. `<a>`) has zero children.
Observing only the target misses the sibling submenu. parentElement captures both.

## Reviewer Findings (4 WARNs, all accepted)
1. WARN: createVisibilityTransitionDetector uses pull model (returns boolean) instead of
   spec's callback push model. Accepted: pull is simpler and functionally equivalent.
2. WARN: hasSize captured but not used in isInvisible(). Accepted: JSDOM returns zeros
   for all bounding rects, would cause false negatives in tests. CSS properties are
   authoritative signals in production.
3. WARN: VISIBILITY_PROPERTIES is documentation-only (not iterated at runtime).
   Fixed: updated comment to clarify it's a reference, not runtime-iterated.
4. WARN: New elements added after baseline not detected by Mechanism 2.
   Accepted: MutationObserver (Mechanism 1) handles this via childList events.

## Architecture
Gate 5 remains implementation-independent:
- Dwell timer callback reads only `candidate.qualified` (Mechanism 1)
  and `detector.compare()` return value (Mechanism 2)
- `commitHover()` receives only the element, not the detection mechanism
- `qualifiedBy` is diagnostic-only, not in HOVER_CAPTURED message or execution JSON
