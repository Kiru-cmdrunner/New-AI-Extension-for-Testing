# C3.3 Root Cause: Visibility Baseline Timing Defect

## Date: 2026-07-15
## Status: CONFIRMED via live browser evidence

## Problem
Both hover interactions on Adani One are still missing after C3.3 implementation.
The C3.3 visibility transition detection code IS in the built extension, but it
cannot detect the transition due to a timing bug.

## Root Cause
**CSS `:hover` is applied by the browser BEFORE the `mouseenter` event fires.**

The content script takes the visibility baseline snapshot at `mouseenter` (line 1069):
```javascript
candidate.baselineVisibility = takeVisibilitySnapshot(visibilityRoot);
```

But at this point, the browser has already applied `:hover` CSS — the submenu's
`display` has already changed from `none` to `block`. So:

- Baseline at mouseenter: `display: block` (already visible)
- At 500ms dwell timer: `display: block` (still visible)
- `detectVisibilityTransition`: baseline.visible == current.visible → NO TRANSITION

## Browser Evidence (Chromium)
Tested with Playwright + real Chrome using exact Adani One CSS pattern:
```
.subMenuParent > .subMenu { display: none; }
.subMenuParent:hover > .subMenu { display: block; opacity: 1; }
```

Results:
- BASELINE (not hovering): display=none
- AT_MOUSEENTER (capture phase): display=block  ← already visible!
- AFTER HOVER SETTLED: display=block

CSS :hover application happens during hit testing, which is BEFORE event dispatch.
So when mouseenter fires, :hover is already in effect.

## Both Mechanisms Fail
- Mechanism 1 (MutationObserver): 0 mutations (CSS-only, no DOM changes)
- Mechanism 2 (Visibility Transition): baseline=current (both display:block)

## Fix Direction
The baseline must be captured BEFORE the user hovers, not at mouseenter.
Options:
1. Take baseline at document load / recording start (too early, but correct)
2. Take baseline periodically and keep last-known state
3. Take baseline of parent state but EXCLUDE the hovered element's :hover effect
   (tricky — :hover affects the parent <li>, not the <a> target)
4. Use `getComputedStyle` with a pseudo-class override (not possible)
5. At mouseenter, briefly check if the element matches :hover and if the
   submenu WOULD be hidden without :hover by reading CSS rules directly

The simplest correct fix: at mouseenter, check the CSS rules to determine
what the "non-hovered" display value would be, rather than reading computed
style (which includes :hover).
