# C3.3 Gate 5 Remaining Viable Approaches — Design Review

**Date:** 2026-07-15
**Status:** Analysis complete, recommendation made
**Context:** DOM Clone Baseline confirmed broken by CSS Context Loss (see c3.3-clone-css-context-loss-root-cause.md)

## Problem Statement
Need a deterministic method to obtain the pre-hover visibility baseline for Gate 5
visibility transition detection, where:
1. The pre-hover state must be captured WITHOUT CSS :hover being applied
2. The capture must preserve the full CSS cascade context (ancestor selectors)
3. The method must work on cross-origin stylesheets
4. No implementation changes have been made — this is design review only

## Approaches Evaluated

### A1: Detach-Reattach (move subtree off-DOM temporarily)
- **Mechanism:** parent.removeChild(target), read getComputedStyle, parent.insertBefore(target, next)
- **CSS Context:** BROKEN — same problem as clone. The CSS selector `.mainNav > ul > li ul.subMenu { display:none }` requires the full ancestor chain. Removing the LI from its parent breaks the chain.
- **Performance:** Tested in earlier benchmarks — comparable to clone
- **Verdict:** ❌ FAILS for same reason as clone

### A2: Stylesheet Rule Analysis (static CSS walk)
- **Mechanism:** Walk document.styleSheets, find :hover rules, match selectors, determine if they modify visibility properties
- **CSS Context:** NOT NEEDED — reads the rules directly, doesn't need to compute them
- **Cross-origin:** FAILS — SecurityError on sheet.cssRules for cross-origin stylesheets
- **Cascade resolution:** FAILS — cannot determine which rule wins (specificity, order, !important)
- **Existing code:** hasNonCosmeticHoverRule() already exists in Gate 3 but NOT used in Gate 5
- **Verdict:** ❌ FAILS for cross-origin + cascade resolution

### A3: Temporarily Disable :hover via StyleSheet API
- **Mechanism:** Walk stylesheets, find :hover rules, replace `:hover` with `:not(#_)` (non-matching pseudo-class), read getComputedStyle, restore
- **CSS Context:** PRESERVED — element stays in DOM, ancestor chain intact
- **Cross-origin:** FAILS — cannot modify cross-origin stylesheet rules
- **Side effects:** Briefly disables ALL :hover on the page (visual flicker)
- **Complexity:** High — must find and replace every :hover rule
- **Verdict:** ❌ FAILS for cross-origin

### A4: Visibility Class Analysis (read computed styles on LIVE DOM at mouseenter)
- **Mechanism:** Just call takeVisibilitySnapshot(target.parentElement) directly at mouseenter
- **Problem:** Confirmed broken — CSS :hover is already applied at mouseenter time
- **Evidence:** hover-0070 baseline showed ALL elements visible (no display:none)
- **Verdict:** ❌ Already confirmed broken

### A5: Mousemove Pre-Arrival Polling
- **Mechanism:** Track mouse position on mousemove, detect when approaching a target, snapshot before hover applies
- **CSS Context:** PRESERVED — reads live DOM
- **Problem:** Non-deterministic — depends on mouse trajectory, speed, approach angle
- **Performance:** High overhead — constant mousemove polling
- **Timing gap:** Cannot guarantee capture before :hover applies (hit-testing happens at sub-pixel level)
- **Verdict:** ❌ Non-deterministic, fragile

### A6: RequestAnimationFrame Polling During Approach
- **Mechanism:** Track all hover-responsive elements, poll their visibility state via rAF, detect transitions from hidden→visible
- **CSS Context:** PRESERVED — reads live DOM
- **Timing:** Catches the transition AS it happens — doesn't need pre-hover baseline
- **Problem:** Still needs to know the "before" state to detect a transition
- **Performance:** Very high — continuous polling of potentially hundreds of elements
- **Verdict:** ❌ Impractical performance

### A7: Detach with Ancestor Preservation (Wide-Scope Detach)
- **Mechanism:** Instead of detaching just target.parentElement, detach a wider ancestor that preserves the CSS selector chain
- **Problem:** We don't know how wide to go. The selector could reference any ancestor.
- **Performance:** Prohibitive — may need to detach the entire <header> or more
- **Complexity:** Must reverse-engineer CSS selectors to determine required ancestor scope
- **Verdict:** ❌ Cannot determine required scope without reading CSS rules (A2 fails)

### A8: Pointer Lock + Temporary :hover Removal via CSS
- **Mechanism:** Inject a `<style>` tag with `* { pointer-events: none !important; }` to remove :hover, read getComputedStyle, then restore
- **CSS Context:** PRESERVED — element stays in DOM
- **Problem:** pointer-events:none does NOT remove :hover (browser still applies :hover based on last hit-test)
- **Evidence:** Confirmed in earlier investigation — setting pointer-events:none does NOT remove :hover
- **Verdict:** ❌ Does not work

### A9: Temporarily Move Cursor via CDP (Chrome DevTools Protocol)
- **Mechanism:** Use chrome.debugger API to move the mouse away from the element, read getComputedStyle, then move back
- **CSS Context:** PRESERVED — element stays in DOM
- **Problem:** Requires `debugger` permission — heavy, prompts the user, security implications
- **UX:** Visible cursor jump — jarring for the user
- **Permissions:** `debugger` permission is flagged by Chrome Web Store
- **Verdict:** ❌ Impractical permissions/UX

### A10: IntersectionObserver + Visibility Transition
- **Mechanism:** Use IntersectionObserver to detect when elements appear/disappear from viewport
- **Problem:** IntersectionObserver detects viewport intersection, not CSS visibility changes
- **Verdict:** ❌ Wrong API — detects scroll, not display:none→block

### A11: Pre-Computed Baseline Cache
- **Mechanism:** On page load (before any hover), snapshot the visibility state of all hover-responsive elements. Use this cached baseline for comparison.
- **CSS Context:** PRESERVED — read from live DOM before any hover
- **Problem:** Must be taken at document_start before any user interaction
- **Problem:** Content may be dynamically loaded (SPA hydration, lazy load)
- **Timing:** May miss dynamically added elements after page load
- **Complexity:** Must keep cache in sync as DOM changes
- **Verdict:** ⚠️ Viable but fragile for dynamic content

### A12: Static :hover Rule Analysis with getComputedStyle Fallback (Hybrid)
- **Mechanism:**
  1. Walk document.styleSheets (same-origin only) for :hover rules that match the target or its subtree
  2. For each matching rule, check if it modifies VISIBILITY_PROPERTIES (display, visibility, opacity)
  3. If yes → the hover IS observable → qualify
  4. If no same-origin match → fall back to live getComputedStyle comparison (clone or other method)
- **CSS Context:** NOT NEEDED for step 1-3 (reads rules, not computed styles)
- **Cross-origin:** PARTIAL — works for same-origin stylesheets, may miss cross-origin rules
- **Adani One case:** Adani One stylesheets ARE same-origin (loaded from assets.adanione.com — same origin as www.adanione.com? Need to verify)
- **Verdict:** ⚠️ Viable for same-origin, partial for cross-origin

### A13: Document.styleSheets :hover Rule Matching (Pure CSS Rule Approach)
- **Mechanism:** Walk all accessible stylesheets, find :hover rules, match the selector against the target and its ancestor chain. If any :hover rule modifies visibility properties (display, visibility, opacity) on the target or its descendants/siblings → qualify.
- **Key insight:** We don't need to know the "before" computed value. We just need to know: "Does a :hover rule change visibility properties on this element's subtree?"
- **Existing code:** hasNonCosmeticHoverRule() ALREADY does this for Gate 3 (on the target itself), but:
  1. It only checks the TARGET element, not its SIBLINGS or DESCENDANTS
  2. It's used for Gate 3 qualification, not Gate 5
  3. It doesn't check if the selector is an ANCESTOR :hover (e.g., `li:hover ul.subMenu`)
- **Enhancement needed:**
  1. Extend to check not just `el.matches(selector)` but also descendants/siblings
  2. Handle ancestor :hover selectors (e.g., `li:hover ul` — the :hover is on the li, the affected element is the ul)
  3. Check if the rule modifies VISIBILITY_PROPERTIES specifically (not just "non-cosmetic")
- **CSS Context:** NOT NEEDED — reads rules directly
- **Cross-origin:** FAILS — SecurityError on sheet.cssRules
- **Verdict:** ⚠️ Strong for same-origin. Cross-origin is the key gap.

### A14: Temporary :hover Suppression via Inline Style Override
- **Mechanism:** Set `target.setAttribute('data-cmdrunner-hover-check', '')` and inject a `<style>` tag:
  ```css
  [data-cmdrunner-hover-check] *:hover,
  [data-cmdrunner-hover-check]:hover,
  [data-cmdrunner-hover-check] ~ *:hover { ... }
  ```
  Wait — this doesn't work. CSS can't override :hover pseudo-class from CSS.

## CRITICAL REALIZATION

All approaches fall into two categories:
1. **Computed Style Approaches** (A1, A4, A5, A6, A11, A14) — Need to read getComputedStyle WITHOUT :hover. Either broken by CSS context loss (clone/detach) or timing (:hover already applied)
2. **CSS Rule Approaches** (A2, A3, A12, A13) — Need to read stylesheet rules. Broken by cross-origin SecurityError.

There appears to be no single approach that handles BOTH:
- CSS :hover timing (need pre-hover state)
- CSS cascade context (need ancestor chain for descendant selectors)
- Cross-origin stylesheets (can't read rules)

## THE KEY INSIGHT

The fundamental problem is: **CSS :hover is a browser-internal state that cannot be queried or suppressed from JavaScript.** The browser applies it during hit-testing, which happens before any event is dispatched. And removing the element from the DOM breaks the cascade context.

This means: **there is no reliable JavaScript API to determine "what would this element's computed style be without :hover?"**

## POTENTIAL BREAKTHROUGH: A15

### A15: Same-Scope Transition Detection (No Baseline Needed)
- **Mechanism:** Instead of comparing "before hover" vs "during hover", detect the transition IN REAL TIME as it happens.
- **Key insight:** At mouseenter, CSS :hover is applied, so we can read the CURRENT state (all visible). But what if we also tracked the state at the PREVIOUS mouseenter (before the mouse entered this element)?
- **Problem:** Previous mouseenter was on a DIFFERENT element, so we don't have a baseline for THIS element.
- **Alternative:** Track ALL hover-responsive elements' visibility states continuously.

### A16: Trigger Mouseleave on Self (Self-Clear :hover)
- **Mechanism:** At mouseenter, programmatically dispatch a mouseleave/mouseout on the target to force the browser to remove :hover, quickly read getComputedStyle, then redispatch mouseenter.
- **Problem:** Synthetic events don't affect :hover — only real mouse movements do.
- **Evidence:** Confirmed — synthetic events have isTrusted=false and don't change :hover.
- **Verdict:** ❌ Cannot control :hover via events

### A17: Width/Height Polling (Layout-Based Detection)
- **Mechanism:** At mouseenter, immediately snapshot the bounding rect dimensions of all elements in the subtree. At dwell timer fire, compare. If any element's width/height changed significantly → something appeared.
- **CSS Context:** PRESERVED — reads live DOM layout
- **Problem:** At mouseenter, :hover is already applied, so the revealed content already has non-zero dimensions. Both "before" and "after" would show the expanded state.
- **Verdict:** ❌ Same timing problem as computed style

## ACTUAL VIABLE APPROACHES (After eliminating all broken ones)

After systematic elimination, only these approaches survive:

1. **A13: CSS :hover Rule Analysis** (same-origin only) — existing hasNonCosmeticHoverRule extended
2. **A11: Pre-Computed Baseline Cache** (captured at page load before first hover)
3. **Hybrid A13+A11+A1** — try CSS rule analysis first, fall back to cache, fall back to clone

But wait — there's one more approach I haven't considered...

### A18: Computed Style Diff with Target Visibility Toggle
- **Mechanism:** Instead of toggling :hover, toggle the element's display/visibility to simulate the "before" state.
- Wait — this doesn't make sense. We need to know what WAS hidden, not force-hide things.

### A19: Query getMatchedCSSRules (deprecated)
- **Mechanism:** window.getMatchedCSSRules() — returns only the CSS rules that matched an element
- **Problem:** DEPRECATED and removed from Chrome since v73 (2019)
- **Verdict:** ❌ Not available

### A20: CSS.containingBlock / CSS.highlights (modern CSS APIs)
- **Mechanism:** Modern CSS Typed OM could potentially query :hover state
- **Problem:** No API exists to query pseudo-class state
- **Verdict:** ❌ No relevant API

### A21: getComputedStyle with pseudo-elt parameter
- **Mechanism:** getComputedStyle(el, ':hover') — but this is for pseudo-ELEMENTS (::before, ::after), not pseudo-CLASSES (:hover)
- **Problem:** The second parameter is for pseudo-elements only, not pseudo-classes
- **Verdict:** ❌ Wrong API

## FINAL CANDIDATE SET

After exhaustive evaluation, the viable approaches are:

1. **CSS Rule Analysis (A13)** — reads stylesheet rules for :hover selectors that modify visibility properties. Extended to cover ancestor :hover and descendant effects. Same-origin only.

2. **Pre-Page-Load Baseline Cache (A11)** — snapshot visibility at page load or before first hover.

3. **Hybrid (A13 + MutationObserver + fallback)** — use multiple mechanisms with OR logic.

The question is: what percentage of real-world sites use cross-origin stylesheets for :hover rules?
- Same-origin: Common for custom-built sites (like Adani One's Next.js app with self-hosted CSS)
- Cross-origin: Common for CDN-hosted CSS (Bootstrap, Tailwind from CDN, etc.)

But here's the thing — **getComputedStyle works regardless of stylesheet origin**. The problem isn't reading the result — it's getting the pre-hover state.

## RECOMMENDATION

**Recommended: A22 — CSS :hover Rule Analysis (Extended) for Gate 5**

Extend the existing hasNonCosmeticHoverRule() to work as a Gate 5 evidence source:
1. Walk accessible stylesheets (same-origin)
2. Find :hover rules that affect the target's subtree
3. Check if they modify VISIBILITY_PROPERTIES (display, visibility, opacity)
4. If yes → Gate 5 qualified

This approach:
- Does NOT need a pre-hover baseline
- Does NOT need CSS cascade context preservation
- Works with Adani One's same-origin CSS
- Uses existing code pattern (hasNonCosmeticHoverRule already exists)
- Preserves the Gate 5 abstraction (candidate.qualified)
- Zero timing dependency

**Risk:** Cross-origin stylesheets (CDN-hosted CSS with :hover rules) won't be caught. But MutationObserver (Mechanism 1) already handles JS-driven menus that modify inline styles.

**Mitigation for cross-origin:** getComputedStyle can detect that a hover-responsive element HAS revealed content (by checking if siblings/descendants have display:block when they should logically be hidden). But this requires knowing the "should be hidden" state — circular.

### A23: Detach-Reattach with Computed Style Diff (No Baseline Needed)
- **Insight:** Instead of detaching to get a "before" baseline, what if we detach to get a "without this element being hovered" state?
- The detached subtree is NOT under the cursor → :hover doesn't apply
- But wait — the detached subtree has BROKEN CSS context (selectors referencing ancestors don't match)
- So the detached computed style is NOT the pre-hover state — it's the "broken context" state

This is the SAME problem as the clone. Detaching breaks CSS context.

## FINAL ANSWER

After exhaustive analysis, the approaches that could work for Adani One are:

1. **CSS Rule Analysis (same-origin)** — A13/A22
2. **Hybrid** — A13 + MutationObserver

Both need the stylesheets to be same-origin. For cross-origin CSS, no reliable approach exists without browser API changes.
