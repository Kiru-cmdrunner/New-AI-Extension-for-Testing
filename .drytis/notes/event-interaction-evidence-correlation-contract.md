# Event → Interaction → BehavioralEvidence Correlation Contract

**Date:** 2026-08-11
**Status:** Design document — not yet implemented
**Baseline:** 35c6034 (root-cause analysis)
**Root cause addressed:** RC-1 (ID mismatch), RC-2 (no attachment), RC-3 (dead deferred map)

---

## 1. Current State — Two Disconnected ID Spaces

### The IDs in play

| ID | Format | Generated by | Present on | Used for |
|----|--------|-------------|------------|----------|
| `eventId` | `evt-{pageId}-{counter}` | EventTap (content script) | `ObservedEvent.eventId` | Identifying raw DOM events |
| `interactionId` | `int-{counter}` | ComponentRuntime (SW) | `ComponentInteraction.interactionId` | Identifying classified interactions |
| `lifecycleId` | `lc-{counter}` | ComponentRuntime (SW) | `ComponentContext.lifecycleId` | Internal lifecycle tracking (not exposed) |

### The implicit mapping that already exists

Every `ComponentInteraction` already carries:
- `triggerEvent: ObservedEvent` — the first event that started this interaction (has `.eventId`)
- `memberEvents: ObservedEvent[]` — all events absorbed into this interaction (each has `.eventId`)

So **the mapping `eventId → interactionId` already exists** inside the ComponentInteraction object itself. It is just never used by the evidence pipeline.

### Why evidence is disconnected

The EvidenceCollector (running in the content script) receives `eventId` from EventTap's `onAfterEvent`. It stores `sourceEventId = eventId` in the BehavioralEvidence. The evidence is delivered to the SW, which broadcasts it with `eventId = sourceEventId`.

But the side panel's matching function compares `eventId` against `interactionId` — two different ID spaces. The mapping data (triggerEvent.eventId) exists on the interaction but is never consulted.

## 2. Design Decisions

### 2.1 Should BehavioralEvidence use `eventId`, `interactionId`, or both?

**Answer: `eventId` only.** Do NOT add `interactionId` to BehavioralEvidence.

**Rationale:**
- Evidence is captured in the content script at event time, before classification. The `interactionId` does not exist yet — it is assigned by the ComponentRuntime in the SW after the event is processed.
- The `eventId` is available at capture time (EventTap assigns it synchronously).
- The mapping `eventId → interactionId` is deterministic: every `ObservedEvent` that triggers or is absorbed into a `ComponentInteraction` is findable via `interaction.triggerEvent.eventId` or `interaction.memberEvents[].eventId`.
- Adding `interactionId` to BehavioralEvidence would require the content script to wait for classification — violating the deferred-evidence-attachment principle (spec §9.1).

**The evidence stays keyed by `sourceEventId` (which IS the `eventId`). The SW does the matching.**

### 2.2 Can one interaction contain multiple source events?

**Yes.** The ComponentRuntime absorbs multiple events into a single lifecycle:
- **Dropdown**: `click` (open trigger) → `click` (option selection) = 2 memberEvents
- **TextEntry**: `focus` → `input` × N → `blur` = N+2 memberEvents
- **DatePicker**: `click` → `click` (date selection) = 2 memberEvents
- **Slider**: `mousedown` → `mousemove` × N → `mouseup` = N+2 memberEvents

**How should evidence be associated with multi-event interactions?**

Each discrete event produces its own BehavioralEvidence window. So one interaction with 2 member events produces 2 evidence objects. But only one of them is the **trigger** — the event that started the interaction.

**Design: evidence is matched to the TRIGGER event only.**

The SW, when receiving BehavioralEvidence with `sourceEventId = X`, searches all live interactions for one whose `triggerEvent.eventId === X`. If found, the evidence is attached to that interaction.

Non-trigger member events' evidence is still stored in `pendingEvidence` (for potential future use) but is NOT attached to the interaction card — the card shows the trigger event's evidence window, which captures the primary user action.

**Why trigger-only:** The trigger event is the one that represents the user's intent (clicking the dropdown, focusing the field). Subsequent events are continuation mechanics (selecting an option, typing characters). The trigger event's evidence window captures the most behaviorally significant moment.

### 2.3 Where should the authoritative mapping be created?

**The Service Worker.** Specifically, the `handleBehavioralEvidence` function.

**Rationale:**
- The SW is the single place where both ComponentInteraction objects and BehavioralEvidence objects coexist.
- The SW already receives both: interactions via `handleObservedEvent` → `processObservedEvent` → `onEmit`, and evidence via `BEHAVIORAL_EVIDENCE` message.
- The SW owns `liveInteractions[]` and persists them to `chrome.storage.local[LIVE_INTERACTIONS_KEY]`.
- No new ID system is needed. The SW uses the existing `triggerEvent.eventId` field on the interaction to match.

### 2.4 How should late-arriving evidence update the correct interaction?

Evidence arrives 300-500ms after the event (the adaptive window needs to stabilize). By then, the interaction has already been emitted, enriched, stored in `liveInteractions`, persisted to `chrome.storage.local`, and broadcast to the side panel.

**The fix:** When evidence arrives, the SW:
1. Finds the matching interaction by `triggerEvent.eventId === sourceEventId`
2. Attaches `evidence` to `interaction.behavioralEvidence`
3. Re-persists `liveInteractions` to `chrome.storage.local`
4. Broadcasts `INTERACTION_EVIDENCE_UPDATE` with the **interactionId** (not the eventId)

**The side panel re-renders the affected card from the stored interaction data**, which now includes `behavioralEvidence`. Or, more efficiently, the side panel finds the card by `interactionId` and calls `updateEvidenceOnInteraction`.

### 2.5 How should the mapping survive side-panel re-renders?

**By attaching evidence to the interaction object itself.** Once `interaction.behavioralEvidence = evidence` is set and re-persisted to `chrome.storage.local`, every subsequent re-render reads the evidence from the stored interaction. The evidence is no longer ephemeral — it is part of the interaction's serialized state.

This eliminates the root cause of RC-2 (evidence lost on re-render) and makes the `__deferredEvidence` fallback (RC-3) unnecessary.

### 2.6 Remove the broken `__deferredEvidence` concept

**Replace with:** A deterministic SW-side matching that uses `interactionId` for the broadcast.

The old design:
```
Content Script → BEHAVIORAL_EVIDENCE → SW → INTERACTION_EVIDENCE_UPDATE { eventId: evt-... }
→ Side Panel searches cards by eventId badge text → NEVER MATCHES
```

The new design:
```
Content Script → BEHAVIORAL_EVIDENCE → SW
→ SW finds interaction by triggerEvent.eventId === sourceEventId
→ SW attaches evidence to interaction.behavioralEvidence
→ SW re-persists to chrome.storage.local
→ SW broadcasts INTERACTION_EVIDENCE_UPDATE { interactionId: int-... }
→ Side Panel finds card by interactionId badge text → MATCHES
→ Side Panel calls updateEvidenceOnInteraction(card, evidence)
```

**No `__deferredEvidence` Map needed.** If the evidence arrives before the card is rendered (unlikely — evidence arrives 300ms+ after the event, cards are rendered near-instantly), the storage-persisted interaction will include the evidence when it IS rendered, because `attachEvidenceDisplay` checks `interaction.behavioralEvidence`.

## 3. Proposed Data Flow

### 3.1 Normal flow (evidence arrives after interaction is displayed)

```
1. User clicks "Login"
   │
   ├─ EventTap fires:
   │    eventId = 'evt-p1a2b-1'
   │    onEvent(observed) → SW: OBSERVED_EVENT
   │    onAfterEvent(targetEl, 'evt-p1a2b-1', 'click')
   │       ↓
   ├─ EvidenceCollector.openWindow(targetEl, 'evt-p1a2b-1', 'click')
   │    → AdaptiveWindow armed (300ms timer)
   │
   ├─ SW: handleObservedEvent(observed)
   │    → ComponentRuntime.process(observed)
   │    → Click definition → immediate completion
   │    → interaction emitted: { interactionId: 'int-1', triggerEvent: { eventId: 'evt-p1a2b-1' }, ... }
   │    → onEmit: enrich + push to liveInteractions + persist to storage
   │    → SW broadcasts INTERACTION_CAPTURED { interaction }
   │    → Side panel renders card: badge text = 'int-1', shows placeholder ⏳
   │
   ├─ ~300ms later: AdaptiveWindow stabilizes → closeWindow
   │    → Builds BehavioralEvidence { sourceEventId: 'evt-p1a2b-1', ... }
   │    → deliverEvidence → SW: BEHAVIORAL_EVIDENCE
   │
   └─ SW: handleBehavioralEvidence(evidence)
        → Search liveInteractions for i.triggerEvent.eventId === 'evt-p1a2b-1'
        → FOUND: interaction int-1
        → interaction.behavioralEvidence = evidence
        → Re-persist liveInteractions to chrome.storage.local
        → Broadcast INTERACTION_EVIDENCE_UPDATE { interactionId: 'int-1', evidence }
        → Side panel: handleEvidenceUpdate('int-1', evidence)
        → Find card with badge 'int-1' → MATCH
        → updateEvidenceOnInteraction(card, evidence) → placeholder replaced
```

### 3.2 Evidence arrives before card is rendered (edge case)

Extremely unlikely (evidence arrives 300ms+ after event, cards render in <50ms), but handled deterministically:

```
SW: handleBehavioralEvidence(evidence)
  → Search liveInteractions for triggerEvent.eventId === sourceEventId
  → FOUND: interaction int-1
  → interaction.behavioralEvidence = evidence
  → Re-persist to storage
  → Broadcast INTERACTION_EVIDENCE_UPDATE { interactionId: 'int-1', evidence }
  → Side panel: no matching card yet (INTERACTION_CAPTURED hasn't been processed)
  → Evidence is now persisted in storage
  → When INTERACTION_CAPTURED arrives → side panel re-renders from storage
  → interaction.behavioralEvidence is already set → renderEvidence() directly
  → No placeholder shown
```

### 3.3 Evidence arrives but interaction not yet in liveInteractions

```
SW: handleBehavioralEvidence(evidence)
  → Search liveInteractions: NOT FOUND
  → Store in pendingEvidence (existing mechanism, keyed by sourceEventId)
  → Do NOT broadcast yet
  → When interaction IS emitted (onEmit callback):
    → Check pendingEvidence for any evidence with sourceEventId matching
      triggerEvent.eventId or memberEvents[].eventId
    → If found: attach immediately, persist, broadcast
```

This is the existing `pendingEvidence` Map doing its job — just with a new consumer (the `onEmit` callback) that drains matching entries.

### 3.4 Navigation events

Navigation evidence is a special case. The EventTap fires `onAfterEvent(document.body, navEventId, 'navigation')`. The EvidenceCollector calls `recordNavigationEvent` which attributes the nav to all open windows — it does NOT open a new window. So navigation evidence is not a standalone BehavioralEvidence; it's metadata within an existing window.

If navigation causes the page to reload (full reload), all in-memory evidence is lost. The `sessionStorage` buffer (spec §9.2) preserves it, but the new page's content script must flush it to the SW. This is an existing M4 design that works correctly.

For SPA navigation (pushState/replaceState), no page reload occurs. The EvidenceCollector creates a window if `navigation` is in `WINDOW_OPEN_EVENTS`. Currently it is NOT — navigation is routed to `recordNavigationEvent` only. This means SPA navigation does not get its own evidence window; it is attributed to whatever window is already open. This is correct behavior.

## 4. Exact Changes Required

### Change 1: SW `handleBehavioralEvidence` — match by triggerEvent.eventId, broadcast interactionId

**File:** `src/background/service-worker.ts`
**Function:** `handleBehavioralEvidence` (line 410)

Current behavior:
```typescript
pendingEvidence.set(evidence.sourceEventId, evidence);
chrome.runtime.sendMessage({
  type: 'INTERACTION_EVIDENCE_UPDATE',
  payload: { eventId: evidence.sourceEventId, evidence },
});
```

New behavior:
```typescript
// Store in pending map
pendingEvidence.set(evidence.sourceEventId, evidence);

// Find matching interaction by triggerEvent.eventId
import { getLiveInteractions } from '../runtime/sw-integration';
const interactions = getLiveInteractions();
const match = interactions.find(
  (i) => i.triggerEvent?.eventId === evidence.sourceEventId
);

if (match) {
  // Attach evidence to interaction
  match.behavioralEvidence = evidence;

  // Re-persist live interactions
  // (call into sw-integration to re-write chrome.storage.local)
  persistLiveInteractionsWithEvidence(interactions);

  // Broadcast with interactionId (not eventId)
  chrome.runtime.sendMessage({
    type: 'INTERACTION_EVIDENCE_UPDATE',
    payload: { interactionId: match.interactionId, evidence },
  });
}
// If no match: evidence stays in pendingEvidence.
// When interaction is emitted (onEmit), check pendingEvidence for a match.
```

### Change 2: SW `onEmit` callback — drain matching pendingEvidence

**File:** `src/runtime/sw-integration.ts`
**Function:** `onEmit` callback in `initRecording()` (line 60) and `restoreFromStorage()` (line 248)

Current:
```typescript
onEmit: (interaction) => {
  enrichInteraction(interaction);
  liveInteractions.push(interaction);
  persistLiveInteractions();
},
```

New:
```typescript
onEmit: (interaction) => {
  enrichInteraction(interaction);

  // Check pendingEvidence for matching evidence
  const triggerId = interaction.triggerEvent?.eventId;
  if (triggerId && pendingEvidence.has(triggerId)) {
    interaction.behavioralEvidence = pendingEvidence.get(triggerId);
    pendingEvidence.delete(triggerId);
  }

  liveInteractions.push(interaction);
  persistLiveInteractions();
},
```

Note: `pendingEvidence` must be accessible from sw-integration. Either:
- Move `pendingEvidence` to sw-integration (preferred — it's session state)
- Export a function `attachPendingEvidence(interaction)` from the SW module

  evt-p1a2b-2 (focus on username input)
  evt-p1a2b-3 (input: 'a')
  evt-p1a2b-4 (input: 'd')

  EvidenceCollector produced ONE BehavioralEvidence with sourceEventId = 'evt-p1a2b-3'

  FALLBACK: check memberEvents
  → evt-p1a2b-3 IS in int-2.memberEvents → MATCH on member

Priority: trigger match > member match. If multiple interactions match (unlikely),
prefer the one whose trigger matches.

**IMPORTANT DESIGN REFINEMENT:** After reviewing the typing case, the initial design of "trigger-only matching" is insufficient. We need two-tier matching:

1. **Tier 1:** `interaction.triggerEvent.eventId === sourceEventId` — preferred
2. **Tier 2:** `interaction.memberEvents.some(e => e.eventId === sourceEventId)` — fallback

This ensures that evidence for non-trigger member events (like the first `input` in a TextEntry) still finds their interaction.

## 7. Edge Cases and Design Decisions

### 7.1 Multiple evidence objects for the same interaction

As shown in Example 4 (dropdown with 2 member events), multiple evidence windows may be produced for events within the same interaction lifecycle.

**Decision: trigger-event evidence wins. First-write-only.**

```
interaction.behavioralEvidence ??= evidence;
```

If `behavioralEvidence` is already set (from the trigger event), subsequent evidence for member events does NOT overwrite it. This is a `first-write-only` / `null-coalescing-assignment` pattern.

### 7.2 Evidence arrives for an event not in any interaction

This happens if:
- The event was deduped by the ComponentRuntime (temporal dedup)
- The event was absorbed by a lifecycle that was then abandoned/interrupted
- The event type is non-discrete (scroll, mousemove) and doesn't produce an interaction

**Decision: evidence stays in `pendingEvidence` Map. It is NOT attached to any interaction. It is NOT displayed. It may be consumed by M8 persistence for audit/debugging purposes.**

### 7.3 Interaction emitted before evidence arrives (the normal case)

This is the standard flow. The interaction card shows a placeholder, then evidence overlays it ~300ms later. This is correct.

### 7.4 Evidence arrives before interaction is emitted

Unlikely but possible — the evidence window closes in 300ms but the ComponentRuntime may hold the event in a longer lifecycle (e.g., a Dropdown lifecycle that waits for option selection).

**Decision: evidence stored in `pendingEvidence`. When interaction is emitted, `onEmit` checks pendingEvidence for matching sourceEventId. If found, attach immediately.**

### 7.5 Unclassified interactions (from Projection Engine)

The Projection Engine creates Unclassified interactions for unclaimed ledger entries. These have:
```typescript
{
  interactionId: 'int-6',
  type: 'Unclassified',
  triggerEvent: { eventId: 'evt-p1a2b-20', ... },
  memberEvents: [],
}
```

The triggerEvent.eventId is populated, so evidence matching works the same way.

### 7.6 Interaction stored without triggerEvent

The `triggerEvent` field is typed as `ObservedEvent` (not optional). However, defensively, the SW matching should guard against `triggerEvent` being null/undefined:

```typescript
const match = interactions.find(
  (i) => i.triggerEvent?.eventId === evidence.sourceEventId
);
```

### 7.7 SW restart (MV3)

On SW restart, `liveInteractions` is restored from `chrome.storage.local`. If evidence was attached before the restart, it is already serialized in the stored interaction. If evidence arrives after the restart, the matching works on the restored interactions.

The `pendingEvidence` Map is lost on SW restart. However, evidence is also buffered in `sessionStorage` (content-script-side), which survives page reloads but NOT SW restarts. For MV3 SW restart recovery, the content script re-sends buffered evidence from sessionStorage on reconnection. This is existing M4 behavior.

## 9. Summary

The root cause is an ID-space mismatch: evidence is keyed by `eventId` (EventTap format `evt-*`), interaction cards are keyed by `interactionId` (ComponentRuntime format `int-*`), and no code bridges them.

The fix does NOT introduce a new ID system. It uses the **existing `triggerEvent.eventId` field** that is already present on every ComponentInteraction. The SW (where both objects coexist) does the matching:

1. Evidence arrives with `sourceEventId` (an eventId)
2. SW searches `liveInteractions` for `triggerEvent.eventId === sourceEventId` (or memberEvents)
3. If found: attach evidence to interaction, re-persist, broadcast `INTERACTION_EVIDENCE_UPDATE` with `interactionId`
4. If not found: store in `pendingEvidence` for later matching when interaction is emitted
5. Side panel matches card by `interactionId` badge text → renders evidence

**No new IDs. No new ID generation. No weakening of ComponentRuntime. Three integration files changed. Deterministic matching with no heuristic fallbacks.**
