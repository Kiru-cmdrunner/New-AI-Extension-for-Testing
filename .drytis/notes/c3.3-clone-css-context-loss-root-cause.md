**Date:** 2026-07-15
**Status:** CONFIRMED via runtime diagnostics

## Root Cause

The DOM Clone baseline strategy FAILS because cloning breaks CSS context-dependent selectors.

Adani One's CSS rule that hides the submenu is:
```css
.PrimaryMenu_mainNav__CviD7 > ul > li.PrimaryMenu_subMenuParent__KNkdB
  ul.PrimaryMenu_subMenu__3NXJv { display: none; }
```

This selector requires the `<li>` to be a descendant of `.PrimaryMenu_mainNav__CviD7 > ul`.
When `takePreHoverSnapshot()` clones the `<li>` and appends it to a `<div>` on `document.body`,
the ancestor chain is broken. The CSS selector no longer matches.

Result: In the clone, the submenu `<ul>` gets default `display:block` instead of `display:none`.
Both baseline (clone) and current (live hovered) show the submenu as visible.
No invisible→visible transition is detected → Gate 5 fails.

## Why Display Values DO Change
The `:hover` CSS modifies parent elements: list-item→inline-block, inline→flex, etc.
But these are visible→visible transitions, not invisible→visible.
The detection logic (`isInvisible → isVisible`) only catches invisible→visible.

## Impact
This affects ALL CSS-only hover menus that use context-dependent selectors to hide content.
The DOM Clone strategy correctly solves the ":hover timing" problem but introduces a new
"CSS context loss" problem.

## Previous Investigation Was Right About the Problem, Wrong About the Solution
- C3.3 initial: baseline captured at mouseenter, :hover already applied → CORRECT diagnosis
- C3.3 fix: DOM Clone to get pre-hover state → solves timing BUT breaks CSS context
- Actual root cause: need a baseline strategy that preserves CSS context AND avoids :hover
