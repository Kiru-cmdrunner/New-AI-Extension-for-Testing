# C6.2 — Universal Date Picker Recording Foundation

**Type:** Implementation  
**Depends On:** C6.1 (frozen), Product Foundation, Architecture, B1–B8, C3–C5

## Objective

Implement the recording layer for Date Picker interactions. Recording only — no changes to Canonical Step generation, Execution JSON, Playwright, Readability Optimizer, or Generation Engine.

## Implementation Mechanisms (from C6.1 §5)

### Mechanism 1: Native HTML Date Inputs
- `input[type=date]`, `datetime-local`, `time`, `month`, `week`
- Detection: `change` event + `input.type` check
- Value: `input.value` is already ISO format
- Display: convert ISO → human-readable (`15 July 2026`)

### Mechanism 2: Calendar Grid (Popover/Inline/Dialog)
- Trigger button + grid/table with date cells
- Detection: `mousedown` on cell inside `[role="grid"]` or calendar container
- Value: cell `aria-label` (preferred), or cell text + calendar header month/year
- Display: from aria-label or reconstructed date

### Mechanism 3: Editable Text Input
- `<input type="text">` with date validation
- Detection: `change` event + value matches date pattern + contextual signals
- Value: parsed from text
- Display: parsed and formatted

## Known Limitations
1. Calendar grid detection uses `aria-label` on cells — ARIA-compliant calendars supported; non-ARIA calendars fall back to cell text + month/year header reconstruction
2. Date range pickers: initial implementation captures each date selection as a separate DateSelect event; coalescing into a single range event is deferred to C6.3
3. Preset range buttons: captured via associated input value change, not the button click
4. Date clearing (empty value) not recorded per C6.1 §3.4
5. Text-input date detection requires contextual signals (calendar icon sibling, date-format placeholder) to avoid false positives on regular text inputs
