## 1. The goal — and the non-goal

**CmdRunner is an Application Understanding Engine.** The end state: given any web application,
the engine understands it the way a human QA engineer does — recognizes controls, correlates
behavioral effects, and derives stable **capabilities** ("search flights", "filter results",
"select departure") that survive UI changes and accumulate across sessions.

**The non-goal — stated three times by the owner, enforced ever since:** site-specific fixes.
AdaniOne (and the clone-harness family) are **validation benchmarks only**. Every fix must work
for *all applications* because it uses platform-standard or industry-convention signals
(ARIA, QA-instrumentation attributes, computed affordances), never site tokens. This was
explicitly re-locked at 7.3 W-B: "make sure the fix is for generic and for all kind of application."

## 3. Current architecture (one screen)

```
DOM capture (EventTap, 15 event types, isTrusted)
  → identity extraction (10-tier accessible name, roles, QA attrs incl. auto-id,
    shadow/iframe context, value/checked before/after routing)
  → classification (16 definitions, Click=fallback@180; claim gates: interactive vocab
    → open-surface (LP1) → QA-instrumentation (W-B))
  → evidence windows (before/after snapshots, domChange summaries, network T1-event-stamp
    attribution, surfaces, navigation, resulting-state scan)
  → understanding pipeline (signal extractors → state builder → causal graph T1–T4
    with confidence floors → episodes/signatures/outcomes)
  → KR (cmdrunner_knowledge, 15 tables; signature identity FROZEN at v1;
    reinforcement per distinct session; demote-not-destroy)
  → generation (IR bridge → ExecutionIRPlan → Playwright) — NEVER imports understanding
  → panel (display honesty; KR browser deep links)
```

**What's strong:** capture breadth, behavioral correlation (T1–T4), KR reinforcement, honesty.
**What's weak (the 2026-08-24 grounding audit, three-way):** classification is
*vocabulary-based* while modern apps express interactivity in CSS; and the entire
semantic layer above episodes (intent = literal button text or HTTP-verb generics;
views = ~30 hardcoded e-commerce URL patterns; no capability vocabulary exists).

## 4. Frozen decisions, doctrine, and lessons learned

**Immutable doctrine (violating any of these reopens solved problems):**
- **Deterministic-first, AI-last.** No timing rules in ownership/classification
  (owner correction 2026-08-20; 6F-M1). No statistics where an attribute fact exists.
- **Honesty over fabrication:** skip ≠ loss. Unclassified is always kept (capture
  guarantee v2). Outcomes never guess ('incomplete', never 'success' without votes).
  Empty strings read as honest absence ('' → null).
- **Generation never imports understanding** (INV-GEN-8/10); one-way derivation.
- **No keyword-dictionary / System-B revival.** Vocabularies must be platform-standard
  (ARIA), industry conventions (QA attrs), or computed DOM facts — never site tokens.
- **Capabilities must be DERIVED from KR** (roadmap 7.3) — the prior 12-rule capability
  engine was deliberately surgically removed (`deff878`); do not rebuild a parallel rule engine.
- **Read-only-KR:** existing rows are never backfilled/rewritten for consistency
  (7.0-KR left old panel-origin app rows inert — separate owner decision if ever).
- **Frozen identities:** `deriveAppId` (v1) and signature key
  `appId:sig:FNV1a(appId|actionType|normalizedTarget|anchorViewId)` — changing either
  orphans all accumulated knowledge. `elementKey` chain order is byte-identity-frozen
  (stableId stays ahead of dataAutoId per 6B).
- **Replay-correctness:** locators must match what capture would claim for the same
  element (the 7.3 landmine: folding bare auto-id into `data-auto-id` would have made
  capture claim elements the executor couldn't resolve — kept as DISTINCT families).

**Lessons learned (each cost a debug cycle):**
1. **Reproduce before fixing.** 6D.2 closed with ZERO implementation because two of its
   three "defects" were NOT-REPRODUCED (O11 pairing already worked via resolveTarget
   ancestor promotion; F4-L has no live repro through any post-6D.1 E2E).
2. **Specs can be wrong.** 6F-M1's frozen arithmetic was falsified by its own E2E;
   corrected spec+tests together, honestly logged. WARN-4's "obvious" fix broke 4/8
   regression pins — the guard is load-bearing.
3. **Audit for starved-of-proof.** 7.1-W2 needed zero code; the chain was complete,
   just unproven. Before writing code, check whether the capability already exists.
4. **Computed-then-discarded is the recurring capture sin.** cursor:pointer and onclick
   are read in `resolveTarget` Strategy 2 (`src/tap/identity-extractor.ts:542-549`) and
   thrown away; `DomContext` declares `ariaValueNow/Min/Max` fields the live extractor
   never fills (only dead-legacy code did). Grep for declared-but-unfilled before
   assuming a gap needs new machinery.
5. **Two-commit closure convention:** commit 1 = src+tests, commit 2 = spec+evidence+
   roadmap. Owner gate BEFORE commit. Publish (push) only on explicit approval —
   publishing is never automatic after a milestone.
6. **Baselines that must hold:** tsc = exactly 8 pre-existing errors; suite count grows
   monotonically (4,669 @ aca8082); ZIP four-way identical (root/download/serve/preview)
   with recorded md5; ZIP mtime can predate the docs commit when src is unchanged —
   verify by dist↔ZIP byte identity + token grep, not by mtime.
7. **Harness truths:** the phase-6e-m1 harness is STALE (pre-6E-M2 expectations, 4 FAILs
   by design — documented, do not "fix"); one suite flake characterized 2026-08-24
   (non-recurring, note saved); harnesses auto-restore /tmp apps.

## 6. The proposed 7.4 direction (owner's hierarchy, audited — NOT yet approved)

The owner proposed a five-stage hierarchy toward human-like understanding:

- **7.4-A Interaction Affordance Understanding** — capture the generic facts that say
  *why* an element is interactive (`pointerCursor`, `clickHandler`).
- **7.4-B Semantic Control Understanding** — combine facts with role/ARIA/DOM/text to
  determine what the control *is* (expander, modal, autocomplete, tab, icon button).
- **7.4-C Behavioral Meaning** — correlate before→action→after→network→navigation→state.
- **7.4-D Capability Understanding** — repeated behavioral patterns → application
  capabilities ("Search flights", "Filter flights").
- **7.4-E Knowledge Reinforcement** — KR proves capabilities stable across sessions/UI changes.

**Grounding-audit verdicts on the hierarchy:**
- 7.4-C is **already ~80% built** (the most mature layer: T1–T4 causal tiers, outcomes,
  state/nav correlation, KR reinforcement). Treat it as existing substrate, not future work.
- 7.4-D is **the true frontier** for the end goal — today no semantic vocabulary above
  "Click/{button text}" exists (intent labels are literal text at conf 0.3 or HTTP-verb
  generics; views are hardcoded e-commerce patterns; the `filter` entity type has NO
  derivation path; `SurfaceView.capabilities` is in-memory only, unpersisted).
- 7.4-A is the correct NEXT slice because it is the root cause of the remaining
  unclassified clicks: modern apps express interactivity in CSS, and classification
  re-checks a static vocabulary. The engine already DETECTS affordance and DISCARDS it
  (`identity-extractor.ts:546-548`, Strategy 2). A = persistence (2 DomContext fields)
  + a third Click claim gate (`pointerCursor || clickHandler`), deterministic, zero
  browser surface, zero site tokens, honest limit preserved (non-pointer non-semantic
  elements stay Unclassified). It unblocks 7.4-B (Expander = affordance + `aria-expanded`
  flip — note classification reads `aria-expanded` NOWHERE today while the behavioral
  layer already emits `control-state-change{expanded}`).
- Queued 7.4-B candidates (generic, evidence-backed): Expander definition on
  `aria-expanded`; Modal definition (role=dialog + surface pairing; `modal-tracker.ts`
  is dead code, `CompoundInteraction` declared-but-undefined); Autocomplete definition
  (combobox + suggestion list + value-write; today typing is swallowed by Dropdown's
  same-element scope); tab-by-class; icon-child class reads; `submit` event ledgering;
  fill the dead `aria-value*` DomContext fields.

**The 13-pattern detect→identify→meaning→effect→capability matrix from the audit lives
in the conversation history of 2026-08-24; its headline: detection is near-universal,
effect-correlation strong, IDENTIFY and CAPABILITY are the broken rungs.**

1. **Read this + the roadmap before touching anything.** Then re-verify the claim in
   source — docs can drift; HEAD is truth.
2. **Grounding audit before every milestone.** Read-only, cite file:line, reproduce the
   symptom, check whether the capability already exists (7.1-W2 lesson), check
   computed-then-discarded and declared-but-unfilled (§4 lesson 4).

   reopen only against a current reproducible failure.

   conflict, correct BOTH together and log it honestly (6F-M1 lesson). When a fix breaks
   regression pins, look for the load-bearing guard (WARN-4 lesson).
5. **No site-specific vocabulary, ever.** If a fix only works for one site, it's wrong.
6. **TDD: red-first pins before implementation.** Unit (vitest/jsdom, fake-indexeddb) +
   integration + real-Chrome E2E for user-visible behavior. Regressions: 6E-M2 DatePicker

   exactly 8, build + ZIP four-way identical with recorded md5, reviewer + infra_verifier
